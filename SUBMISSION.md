# Сдача проекта «СвойДом» — команда We_Use_GPT

Этот файл собирает материалы для технической проверки. Пользовательский запуск,
состав сервиса и порядок работы описаны в [README.md](README.md). Здесь отдельно
отмечены готовые артефакты и то, что нужно подтвердить непосредственно перед
сдачей. Не добавляйте в репозиторий `.env`, токен бота, ключ GigaChat, реальные
телефоны или подписанные данные запуска MAX.

На первом техническом слайде PDF укажите ссылку на бота/мини-приложение в MAX,
ссылку на Git-репозиторий и полный хеш коммита, адрес API, способ получить
доступ для трёх тестовых ролей и краткий порядок проверки. Секреты и
действующие ключи передавайте проверяющим отдельно защищённым способом: в
публичный репозиторий и общедоступный PDF их не помещайте. Статический
`X-Max-Init-Data` в PDF не подходит, потому что данные запуска действуют один
час. Если для оценки требуется именно постоянный логин/пароль или токен,
текущая MAX-авторизация такого режима не предоставляет — это нужно отдельно
оговорить с проверяющими, а не обещать несуществующие учётные записи.

Начиная со второго слайда PDF покажите название и состав команды, краткий
результат, целевую аудиторию и проблему, основной сценарий жителя и УК,
ожидаемый эффект, архитектуру и интеграции, условия масштабирования,
ограничения и использованные источники. Работу функций демонстрируйте на
реальном MAX-клиенте, а не только скриншотами контейнеров.

## Воспроизводимый запуск и внешние условия

Подготовьте `.env` по `.env.example`; значения `BOT_TOKEN`, `PORT`, `DB_*` и
`FILE_STORAGE_ROOT` обязательны. Затем из корня репозитория запустите
`docker compose up --build`. Миграции выполняются до запуска приложения и бота.
Локально порт FastAPI открыт только на `127.0.0.1:${PORT}`; PostgreSQL доступен
лишь внутри сети Compose. На боевом VPS Nginx завершает HTTPS на порту 443 и
проксирует запросы к локальному FastAPI. Для загрузки файлов в HTTPS-блоке
Nginx задано `client_max_body_size 10m`. Внешний MAX нужен для входа и бота;
GigaChat — необязательная подсказка к тексту проблемы, при сбое действует
локальный запасной алгоритм. Содержимое PostgreSQL и приватные вложения
сохраняются в отдельных томах Docker.

Для финальной проверки на VPS выполните `docker compose config --quiet`,
измерьте холодную сборку командой `time sudo docker compose build --no-cache`
(после первоначальной загрузки базовых образов), затем `docker compose ps`,
`curl -fsS https://168.113.209.86/service/ready` и сквозной сценарий ниже.
Сборку на этом рабочем компьютере не измеряли: Docker здесь отсутствует.
Останавливайте сервис без потери данных командой `docker compose down`,
возобновляйте командой `docker compose up -d --build`. `down -v` удаляет тома
БД и вложений; для обычной остановки он не нужен.

## Тестовые аккаунты и тестовые данные

Для основного сценария нужны **три разных аккаунта MAX**: представитель УК,
житель А и житель Б. Каждый подтверждает свой телефон через MAX; общих
логина/пароля у сервиса нет. В штатном режиме оператор поддержки отдельно
проверяет регистрацию УК и подключение дома. Чтобы проверяющие не зависели от
оператора, на время теста можно включить `TEST_MODE=1` в серверном `.env`:
представитель УК подаёт обычную заявку и нажимает выделенную кнопку тестового
подтверждения. Так создаются первый сотрудник УК и её дома. Это **не** обходит
вход MAX или подтверждение телефона. В обычном режиме `TEST_MODE=0` маршрут
тестового подтверждения возвращает `404`. После проверки верните `0` и
пересоздайте контейнер приложения; оставлять публичный обход включённым нельзя.

[submission/test-data.json](submission/test-data.json) — вымышленные имя УК,
адрес дома, число подъездов и квартир, данные двух жильцов и тексты похожих
проблем. Это входные данные **для ручного ввода**, а не автоматическая загрузка
в БД. Номера телефонов берутся от тестовых аккаунтов MAX, поэтому в файле их
нет. Таким образом «тестовые данные» отличаются от «тестовых учётных записей»:
первые воспроизводят предметный сценарий, вторые задают, кто его выполняет.
При повторном прогоне на той же БД используйте новый вымышленный номер дома:
один и тот же адрес нельзя подключить повторно.

Сквозная проверка: представитель создаёт УК и дом; оба жителя подают заявки
на доступ; сотрудник одобряет их; житель А создаёт проблему лифта; житель Б
поддерживает существующую карточку; сотрудник пишет ответ и переводит её
«В работе». Ожидается одна общая карточка с двумя участниками, видимый ответ
и одинаковый статус в мини-приложении и боте. Более подробные шаги и
ограничения есть в README.md.

## Собственный API

- Базовый HTTPS-адрес: <https://168.113.209.86>.
- Живое описание: <https://168.113.209.86/openapi.json>.
- Сдаваемый полный снимок OpenAPI 3.1: [openapi.json](openapi.json), полученный
  из работающего FastAPI-приложения командой
  `cd backend && python -m tools.export_runtime_openapi`.
- Проверки основного сценария: [DATA-API.yaml](DATA-API.yaml). Версия схемы,
  продукт/команда, базовый адрес, метод, путь, параметры, роль, ожидаемые коды
  и формат ответа указаны для каждой проверки.

`backend/openapi.yaml` служит входом внутреннего кодогенератора и содержит
только его маршруты. Для сдачи используйте корневой `openapi.json`: он
включает также файлы, админские и служебные методы. После последнего
изменения кода **заново экспортируйте** этот файл, проверьте
`python -m tools.export_runtime_openapi --check` и сравните с опубликованным
`/openapi.json` после развёртывания. На 30 сентября локальный снимок содержит
71 маршрут, а ранее развёрнутый API — 68; до финальной выкладки они ещё не
совпадают. При смене публичного адреса обновите `api.baseUrl` в DATA-API и
перегенерируйте схему с `--server-url https://НОВЫЙ-АДРЕС`.

OpenAPI отвечает на вопрос «какие маршруты, поля и ответы поддерживает API».
DATA-API.yaml — отдельный список **конкретных проверок** для сценария оценки:
какая роль делает запрос и что должно получиться. Один файл не заменяет
другой. Поскольку на слайде перечислены обязательные поля, но нет ссылки на
машиночитаемую схему DATA-API, структура нашего файла явно отражает именно
эти поля; если проверяющие дадут точную схему, её надо сверить перед отправкой.

Закрытые маршруты требуют заголовок `X-Max-Init-Data` со свежими подписанными
данными запуска **соответствующего** аккаунта MAX. Он не является постоянным
API-ключом; срок действия — один час. Для прямой проверки API данные можно
взять из `window.WebApp.initData` в открытом через MAX мини-приложении, не
публикуя их. `DATA-API.yaml` использует переменные вместо реальных значений.
`HOUSE_ID` берётся из поиска дома, `CATEGORY_ID` — из списка категорий,
`REQUEST_ID` и `CARD_ID` — из предыдущих ответов. Для POST-запросов нужны
разные `Idempotency-Key`: повтор с тем же ключом может вернуть `409`.

## Что остаётся перед отправкой

1. Развернуть **финальный** коммит и убедиться, что бот и мини-приложение
   открываются в MAX, а опубликованный OpenAPI соответствует файлу в коммите.
2. Прогнать сценарий с трёх отдельных MAX-аккаунтов, проверить работу вложений
   и зафиксировать наблюдаемые результаты.
3. Измерить холодную Docker-сборку на машине сдачи и убедиться, что она
   укладывается в лимит 5 минут; при необходимости оптимизировать.
4. Создать PDF, вписать ссылку на MAX, адрес API, ссылку на репозиторий и
   полный хеш финального коммита; передать доступы проверяющим безопасно.
5. Выключить `TEST_MODE`, если проверка закончена, либо явно ограничить период
   тестирования и осознавать, что в этом режиме саморегистрация УК открыта.
