# Проверка сервиса «СвойДом»

«СвойДом» — сервис обращений жителей домов и управляющих компаний в MAX.
Житель получает доступ к своему дому, сообщает о проблеме и следит за её
решением. Сотрудник УК подтверждает доступ жителей, отвечает на обращения и
публикует статус работ. Те же предметные действия доступны в мини-приложении
и текстовом диалоге с ботом. Команда проекта — We_Use_GPT.

## Адреса и материалы

- Мини-приложение и API: <https://168.113.209.86/>. Для входа откройте
  мини-приложение **из бота MAX**: обычный переход по адресу в браузере не
  передаёт подписанные данные запуска.
- Исходный код: <https://github.com/ByterGame/hackathon_max_2026>.
- [README.md](README.md) — окружение, архитектура и запуск;
  [submission/test-data.json](submission/test-data.json) — вымышленные данные
  для сценариев ниже; [DATA-API.yaml](DATA-API.yaml) — проверки собственного API.
- Рабочие токены и подтверждённые номера не размещаются в репозитории.
  Авторизация пользователей выполняется через MAX, а не по общему паролю.

## Запуск и внешние условия

Для локального запуска создайте `.env` по [.env.example](.env.example). Нужны
токен бота, параметры PostgreSQL, порт приложения и каталог вложений. Из корня
репозитория выполните одну команду:

```sh
docker compose up --build
```

Compose запускает PostgreSQL, выполняет миграции, затем поднимает HTTP-сервис
и бота. `docker compose ps` показывает состояние процессов. У работающего
сервиса `GET /service/health` и `GET /service/ready` отвечают
`{"status":"ok"}`. На VPS HTTPS-запросы принимает Nginx; контейнер FastAPI
доступен хосту только через `127.0.0.1:${PORT}`, порт PostgreSQL наружу не
опубликован. MAX нужен для входа и сообщений бота. GigaChat используется для
подсказок к проблеме, но при его недоступности подача не блокируется.
PostgreSQL и приватные вложения хранятся в отдельных томах Docker.

Остановка без удаления данных: `docker compose down`. Повторный запуск:
`docker compose up -d --build`. Команда `docker compose down -v` удаляет тома
с данными и для обычной остановки не применяется.

## Участники и тестовые данные

Для сценариев 1–8 нужны три **разных аккаунта MAX** с подтверждёнными
номерами: представитель УК, житель А и житель Б. Для сценария 9 требуется
четвёртый аккаунт сотрудника. Аккаунт MAX служит способом
входа, отдельного логина и пароля нет. Сотрудник и жилец не могут быть одной
ролью в одном аккаунте. [Тестовые данные](submission/test-data.json) задают
вымышленные «УК Тестовый квартал», дом на два подъезда и 40 квартир, жильцов
квартир 12 и 13 первого подъезда и тексты обращений о лифте. Файл не
загружается в БД автоматически: данные вводятся через интерфейс. Участники
используют собственные номера MAX; реальные телефоны и ключи в файле не
публикуются. Для повторной регистрации на той же БД укажите новый вымышленный
номер дома, потому что подключённый адрес нельзя добавить второй раз.

Штатное подключение УК рассматривает оператор поддержки. Если на проверочном
сервере включён `TEST_MODE=1`, новый представитель может подтвердить свою
заявку на УК без оператора через выделенную кнопку. Номер первого сотрудника в
заявке должен совпадать с его подтверждённым номером MAX. Тестовый режим не
заменяет вход через MAX и подтверждение телефона. При `TEST_MODE=0` кнопка
недоступна, а запрос к тестовому маршруту возвращает `404`. При `TEST_MODE=1`
самоподтверждение доступно любому новому пользователю с подтверждённым номером,
поэтому этот режим предназначен только для проверочной среды.

## Основные сценарии и ожидаемое поведение

Сценарии идут в порядке, в котором создаются нужные данные. Все действия,
кроме проверки публичных HTTP-маршрутов, выполняются из мини-приложения,
открытого через MAX. Там, где используется бот, указан отдельный текстовый
путь к той же записи.

### 1. Подключение УК и дома

Представитель подтверждает номер, открывает «Подключить УК» и вводит название,
свой номер как номер первого сотрудника, пояснение и адрес из тестовых данных.
Для дома указывает 2 подъезда и 40 квартир. В тестовом режиме после отправки
нажимает «Создать тестовую УК без проверки»; в штатном режиме решение принимает
поддержка через бота.

Ожидается: после одобрения у представителя появляется кабинет УК с тремя
правами — управление сотрудниками, доступами жильцов и проблемами. Дом
находится поиском по адресу. До одобрения регистрация остаётся заявкой с
доступным обсуждением, а компания и дом не выдаются за подключённые.

### 2. Заявка жителя на доступ

Жители А и Б по отдельности подтверждают свои номера, находят подключённый
дом, проверяют совпавший адрес и указывают ФИО, первый подъезд и квартиры 12
и 13 соответственно. Каждый отправляет свою заявку. Сотрудник УК открывает
«Доступы» → «Заявки на доступ», может ответить в обсуждении, затем выдаёт
доступ с пояснением. При выдаче можно выбрать бессрочный или ограниченный
датой доступ.

Ожидается: до решения жилец видит собственную заявку и обсуждение, но не
проблемы дома. После одобрения дом появляется в «Моих домах», а доступ к
проблемам соответствует выданной квартире и сроку. Номер квартиры больше
числа квартир дома или номер подъезда вне диапазона не принимается.

### 3. Создание проблемы и область видимости

Житель А выбирает категорию, пишет описание и указывает область «Квартира».
Создаёт вторую карточку с областью «Подъезд». Сервер определяет квартиру и
подъезд по действующему доступу; произвольно выбрать чужие номера нельзя.
При нескольких своих квартирах в одном доме житель выбирает нужную привязку.
На финальном шаге проверяет предложенные название и сводное описание, при
необходимости исправляет их и нажимает «Создать заявку».

Ожидается: проблему квартиры 12 видят жилец А и сотрудник УК, но не жилец Б
из квартиры 13. Проблему первого подъезда видят оба жителя и сотрудник УК.
Исходное описание хранится отдельно от сводного. Если GigaChat недоступен,
используется локальная подсказка, а отправка остаётся доступной.

### 4. Вложения и приватность файлов

Житель А выбирает несколько вложений при создании проблемы либо добавляет их
после открытия карточки. Вложения также можно добавить к заявке на доступ к
дому. Допустимые типы и предел размера приведены в
[правилах файлов](backend/docs/files/README.md).

Ожидается: изображения показываются в карточке, для PDF и видео отображается
обозначение типа и доступно скачивание. Жилец Б не получает файл из
квартирной карточки А даже по прямой ссылке. Файл из заявки на доступ видят
только участники этой заявки.

### 5. Похожая проблема и поддержка

Используйте подъездную карточку о лифте из сценария 3. Житель Б сообщает о той же
поломке и подтверждает подходящую найденную карточку либо открывает её в
списке и нажимает «У меня та же проблема».

Ожидается: остаётся одна общая карточка с двумя уникальными участниками.
Повторная поддержка тем же человеком не увеличивает счётчик. Автоматическое
предложение совпадения не гарантируется: окончательное решение о поддержке
принимает жилец, а карточка всегда доступна для ручного выбора в списке.

### 6. Ответ УК, статусы и повторное открытие

Сотрудник УК отвечает в обсуждении карточки, переводит её «В работе» с
пояснением, затем закрывает с результатом и обязательной причиной. Жилец А
после закрытия переоткрывает свою карточку, указав комментарий.

Ожидается: статус, пояснение и обсуждение видны жителям с доступом. Просмотр
карточки или комментарий жителя сами по себе статус не меняют. После
переоткрытия статус снова «Открыта»; житель Б, который лишь поддержал
карточку, переоткрыть её не может.

### 7. Объединение карточек сотрудником УК

Для того же дома создаются две открытые карточки об одной проблеме. Сотрудник
УК открывает действие объединения, проверяет итоговые поля и подтверждает
его. Закрытая карточка в объединении не участвует.

Ожидается: основной становится более ранняя карточка; исходные сообщения,
вложения, история и участники обеих карточек сохраняются. Один человек,
поддержавший обе, учитывается в итоговом счётчике один раз. Переход по ссылке
на присоединённую карточку открывает итоговую.

### 8. Уведомления и текстовый бот

После новых заявок, ответов и изменения статуса проверяются сообщения бота и
раздел уведомлений мини-приложения. Нажатие на уведомление открывает нужную
заявку или проблему. Кнопка «Прочитать все» снимает отметки непрочитанного.
У бота `/start` показывает меню; команды `/access help`, `/issuehelp` и
`/notificationhelp` открывают текстовые действия с теми же данными.

Ожидается: изменения, сделанные в мини-приложении, видны через бота и
наоборот. Отключение сообщений бота для конкретной карточки не убирает её из
раздела уведомлений мини-приложения.

### 9. Права сотрудников УК

Для проверки выдачи прав нужен ещё один аккаунт MAX. Сотрудник с правом
управления персоналом приглашает его по номеру и назначает нужные права.
Приглашённый подтверждает свой номер; назначение автоматически связывается с
его аккаунтом без отдельного принятия.

Ожидается: просмотр данных домов УК доступен сотруднику, а изменение
доступов жителей, проблем и состава сотрудников зависит от выданных прав.
Сотрудник не может изменить или отозвать собственное назначение.

### 10. Предложение доступа и отмена заявки

Сотрудник УК с правом управления жильцами открывает «Предложить доступ по
номеру» и предлагает жильцу Б доступ к другой квартире того же дома,
например № 14. Указывает его уже подтверждённый номер MAX. Жилец Б принимает
либо отклоняет предложение. Для проверки отмены он подаёт отдельную заявку
на ещё одну квартиру, например № 15; пока она открыта, отменяет её сам. Для
отдельной заявки на квартиру № 16, переведённой УК «На рассмотрении», отмена
проходит через запрос одной стороны и ответ другой.

Ожидается: одно только предложение не выдаёт доступ; он появляется лишь после
принятия владельцем подтверждённого номера. Открытую заявку её автор может
отменить сам. В рассматриваемой заявке статус «Отменена» появляется только
после подтверждения второй стороной; обсуждение сохраняется.

## Собственный API

- Базовый HTTPS-адрес: <https://168.113.209.86>.
- Описание методов и форматов OpenAPI 3.1:
  <https://168.113.209.86/openapi.json> и [файл в репозитории](openapi.json).
- Последовательность девяти проверок с ролями, параметрами и ожидаемыми
  ответами: [DATA-API.yaml](DATA-API.yaml).

OpenAPI описывает доступные методы, тела запросов и ответы. DATA-API.yaml
задаёт конкретные контрольные запросы для сценария выше; файлы выполняют
разные задачи. Для проверки полного API используется корневой `openapi.json`,
включая маршруты файлов, администрирования и служебных проверок.
Проверки DATA-API воспроизводят действия сценариев 2–6 на **свежих данных**,
а не повторяются после них на той же квартире: повторная выдача уже
существующего доступа возвращает `409`.

Закрытые маршруты требуют заголовок `X-Max-Init-Data` со свежими подписанными
данными запуска **соответствующего** аккаунта MAX. Он не является постоянным
API-ключом; срок действия — один час. Для прямой проверки API данные можно
взять из `window.WebApp.initData` в открытом через MAX мини-приложении, не
публикуя их. `DATA-API.yaml` использует переменные вместо реальных значений.
`HOUSE_ID` берётся из поиска дома, `CATEGORY_ID` — из списка категорий,
`REQUEST_ID` и `CARD_ID` — из предыдущих ответов. Для POST-запросов нужны
разные `Idempotency-Key`: повтор с тем же ключом может вернуть `409`.
