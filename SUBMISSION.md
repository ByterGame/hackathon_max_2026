# Проверка сервиса «СвойДом»

«СвойДом» — сервис обращений жителей домов и управляющих компаний в MAX.
Житель получает доступ к своему дому, сообщает о проблеме и следит за её
решением. Сотрудник УК подтверждает доступ жителей, отвечает на обращения и
публикует статус работ. Те же предметные действия доступны в мини-приложении
и текстовом диалоге с ботом. Команда проекта — We_Use_GPT.

## Адреса и материалы

- Мини-приложение и API: <https://168.113.209.86/>. Для входа откройте
  мини-приложение **из бота MAX**: обычный переход по адресу в браузере не
  передаёт подписанные данные запуска.
- Исходный код: <https://github.com/ByterGame/hackathon_max_2026>.
- [README.md](README.md) — назначение сервиса, технологии и запуск;
  [submission/test-data.json](submission/test-data.json) — вымышленные данные
  для сценариев ниже; [DATA-API.yaml](DATA-API.yaml) — проверки собственного API.
- Рабочие токены и подтверждённые номера не размещаются в репозитории.
  Авторизация пользователей выполняется через MAX, а не по общему паролю.

## Участники и тестовые данные

Для сценариев 1–8 нужны три **разных аккаунта MAX** с подтверждёнными
номерами: представитель УК, житель А и житель Б. Для сценария 9 требуется
четвёртый аккаунт сотрудника. Аккаунт MAX служит способом
входа, отдельного логина и пароля нет. Сотрудник и жилец не могут быть одной
ролью в одном аккаунте. [Тестовые данные](submission/test-data.json) задают
вымышленные «УК Тестовый квартал», дом на два подъезда и 40 квартир, жильцов
квартир 12 и 13 первого подъезда и тексты обращений. Файл не
загружается в БД автоматически: данные вводятся через интерфейс. Участники
используют собственные номера MAX; реальные телефоны и ключи в файле не
публикуются. Для повторной регистрации на той же БД укажите новый вымышленный
номер дома, потому что подключённый адрес нельзя добавить второй раз.

Штатное подключение УК и её домов рассматривает оператор поддержки. Если на
проверочном сервере включён `TEST_MODE=1`, представитель может создать УК и
дом без оператора через выделенную кнопку. Его подтверждённый в MAX номер
должен совпадать с номером первого сотрудника в заявке. Тестовый режим не
заменяет вход через MAX и подтверждение телефона; при `TEST_MODE=0` кнопки
нет. Проверочный режим предназначен только для среды тестирования.

## Основные сценарии и ожидаемое поведение

Сценарии идут в порядке, в котором создаются нужные данные. Все действия,
кроме проверки публичных HTTP-маршрутов, выполняются из мини-приложения,
открытого через MAX. Там, где используется бот, указан отдельный текстовый
путь к той же записи.

### 1. Подключение УК и дома

1. Представитель УК открывает бот MAX и мини-приложение из него. На экране
   «Подтвердить номер» нажимает «Подтвердить номер в MAX» и передаёт **свой**
   номер.
2. На стартовом экране «Подключить дом» нажимает «Подключить УК».
   В блоке «Управляющая компания» вводит «УК Тестовый квартал», свой
   подтверждённый номер в поле «Номер первого сотрудника» и пояснение из
   [тестовых данных](submission/test-data.json) в «Пояснение для поддержки».
3. В блоке «Дома для подключения» вводит адрес
   «г. Тестоград, ул. Проверочная, д. 730», количество подъездов `2` и
   количество квартир `40`. Нажимает «Отправить заявку».
4. На проверочном сервере с `TEST_MODE=1` в блоке «Только для тестирования»
   отмечает «Понимаю, что это тестовый обход проверки», нажимает
   «Создать тестовую УК без проверки», затем «Открыть кабинет УК».
   В обычном режиме этого блока нет: оператор поддержки проверяет отдельно
   обращение об УК и заявку на дом. До его решения представитель открывает
   «Открыть заявку и обсуждение», чтобы видеть состояние и переписку.
5. В кабинете УК представитель открывает «Доступы» → вкладку «Дома» и в
   блоке «Дома УК» проверяет, что адрес подключён, показаны 2 подъезда и 40 квартир.
   Новый дом после регистрации добавляется там же через «Запросить подключение
   дома» → «Отправить заявку»; его тоже проверяет поддержка. Сотрудник УК
   самостоятельно не подтверждает заявку на новый дом.

**Ожидается:** после подключения представитель получает права управления
сотрудниками, доступами жильцов и проблемами. До решения поддержки в обычном
режиме компания и дом не считаются подключёнными. Для повторной проверки на
той же БД потребуется новый вымышленный адрес.

### 2. Заявка жителя на доступ

1. Жилец А со своего аккаунта MAX открывает мини-приложение, нажимает
   «Подтвердить номер в MAX», затем на экране «Подключить дом» нажимает
   «Подать заявку на доступ».
2. На странице «Доступ к дому» в блоке «Найдите подключённый дом» вводит
   `Проверочная`. В «Совпадающие адреса» выбирает точный адрес из
   сценария 1 и отмечает «Подтверждаю адрес: …». Если адрес не появился,
   сначала проверьте подключение дома в сценарии 1.
3. В «Ваши данные» вводит ФИО «Тестов Иван Иванович», подъезд `1` и квартиру
   `12`; нажимает «Отправить заявку в УК». На экране результата нажимает
   «Открыть заявку и обсуждение». Там видны состояние заявки и переписка;
   написать УК можно до выдачи доступа. Если этот аккаунт MAX уже подавал
   заявки, вместо поля ФИО показано «ФИО в общем профиле»; при необходимости
   сначала нажмите «Изменить ФИО».
4. Жилец Б **с другого аккаунта MAX** повторяет шаги 1–3 с ФИО
   «Примерова Анна Петровна», подъездом `1`, квартирой `13`. При последующих
   подключениях ФИО берётся из общего профиля аккаунта, а не запрашивается
   заново для каждого дома.
5. Представитель УК открывает кабинет → «Доступы» → вкладку «Жильцы» →
   «Заявки на доступ». Для заявки квартиры 12 нажимает «Обсуждение»;
   при необходимости пишет в поле «Ответить в обсуждении» и нажимает
   «Отправить». Затем нажимает «Решение», в открывшемся ниже блоке выбирает
   «Выдать доступ», срок «Постоянный», вводит пояснение, например
   «Данные проверены», и нажимает «Сохранить решение».
6. Тем же способом выдаёт доступ жителю Б к квартире 13. Для проверки
   временного доступа в поле срока можно выбрать «Временный» и указать дату
   окончания. Оба жителя обновляют мини-приложение и на главной странице
   проверяют раздел «Мои дома»: подключённый дом должен появиться там.

**Ожидается:** до решения жилец видит свою заявку и обсуждение, но не проблемы
дома. После выдачи доступны проблемы по правилам видимости его квартиры,
подъезда и дома. Квартира за пределами `1–40` или подъезд вне `1–2` не
принимаются.

### 3. Создание проблемы и область видимости

1. Жилец А на главной странице проверяет дом из сценария 1 в «Мои дома».
   Если домов несколько, выбирает нужный; если дом один, он уже выбран.
   Нажимает «+ Сообщить о проблеме»;
   тот же экран доступен через нижнюю кнопку «Создать».
2. В первом шаге выбирает категорию «Электричество». В «Опишите проблему»
   вводит: «В квартире 12 с утра нет электричества. Свет и розетки не
   работают, автоматы в щитке включены.». В области проблемы выбирает
   «Квартира». Если у него несколько квартир, указывает **свою** квартиру 12.
   Нажимает «Продолжить».
3. На экране «Мы поняли проблему так» проверяет название и сводку. При
   необходимости нажимает «Изменить название и сводку» и правит их; для
   создания карточки нажимает именно «Создать заявку». Это квартирная
   карточка, доступная автору и УК.
4. Жилец А снова открывает «Создать» или «+ Сообщить о проблеме». Выбирает
   категорию «Лифт», вводит текст: «В первом подъезде лифт не реагирует на
   кнопку вызова и стоит на первом этаже.», область «Подъезд» и свой подъезд
   `1`, затем «Продолжить» → «Создать заявку». Запомните эту **первую
   подъездную карточку о лифте**: она понадобится в сценариях 5–7.
5. Жилец Б открывает «Проблемы» → «Активные» → «Все» и проверяет, что видит
   подъездную карточку о лифте, но не квартирную карточку А. Представитель УК
   открывает «Проблемы» и видит обе. В карточке А раскройте «Исходные
   обращения»: там должен остаться введённый текст, даже если название и
   сводка на предыдущем шаге были изменены.

**Ожидается:** область и номера берутся из выданного доступа; указать чужую
квартиру нельзя. Исходный текст сохранён отдельно от названия и сводки.
Если GigaChat недоступен, применяется локальная подсказка; создание не
блокируется.

### 4. Вложения и приватность файлов

1. Жилец А открывает свою квартирную карточку из сценария 3. В блоке
   «Обсуждение» нажимает «Прикрепить файлы к сообщению», выбирает сразу
   несколько файлов, например изображение и PDF, при необходимости пишет
   сообщение и нажимает кнопку «Отправить». Несколько файлов можно выбрать
   также **до** создания проблемы: первый шаг формы → «Фото, видео и
   материалы» → «+ Добавить».
2. В открытой карточке проверяет вложения **у отправленного сообщения**:
   изображение просматривается прямо в интерфейсе, у PDF и видео видны
   обозначения типа и кнопка «Скачать». Файлы, выбранные
   ещё при создании проблемы, показываются в отдельном блоке «Вложения».
   Допустимые форматы и ограничение размера
   показаны рядом с выбором файлов и описаны в
   [правилах файлов](backend/docs/files/README.md).
3. Жилец Б открывает список «Проблемы» и проверяет, что квартирной карточки А
   там нет. При проверке API прямая ссылка на файл из этой карточки от имени
   Б также не должна выдавать файл. Сотрудник УК, открыв эту карточку в
   разделе «Проблемы», видит вложения.
4. Для проверки вложения в заявке на доступ Б открывает вкладку «Доступ».
   На экране «Доступ к дому» снова находит тот же дом, указывает подъезд `1`
   и новую квартиру `17`, а в блоке «Вложения для УК» нажимает «Выбрать
   файлы» **до** кнопки «Отправить заявку в УК». Файлы видны Б и УК в
   карточке этой заявки, но не остальным жильцам.

**Ожидается:** все выбранные файлы доступны только участникам соответствующей
карточки или заявки. Новую заявку Б на квартиру 17 можно оставить открытой;
доступ к этой квартире сам по себе не появляется.

### 5. Похожая проблема и поддержка

1. Жилец Б из квартиры 13 нажимает «Создать» (или «+ Сообщить о проблеме»
   на странице дома). Выбирает категорию «Лифт», область «Подъезд» и подъезд
   `1`. В «Опишите проблему» вводит: «Лифт в нашем подъезде не приезжает
   после нажатия кнопки. Кабина остается внизу.». Нажимает «Продолжить».
2. Если появился блок «Похоже, об этой проблеме уже сообщили», сверяет дом,
   подъезд и содержание с **первой подъездной карточкой А из сценария 3** и
   под ней нажимает «У меня та же проблема». Кнопку «Создать заявку» в этом
   случае не нажимает: она создаст вторую карточку.
3. Если подсказка не появилась, возвращается к дому, открывает «Проблемы»
   или «Все проблемы дома» → «Активные» → «Все», находит **эту же первую
   карточку** по описанию и области «Подъезд», открывает её и нажимает
   «У меня та же проблема» в карточке. Название, предложенное моделью, может
   отличаться от введённого текста, поэтому ориентируйтесь и на описание.
4. Повторно откройте карточку из аккаунтов А и Б и посмотрите число
   поддержавших. У Б кнопка повторной поддержки заблокирована и подписана
   «Вы участвуете» (на экране предложения совпадения — «Вы уже участвуете»).

**Ожидается:** существует одна карточка о лифте с двумя уникальными
участниками. Повторное действие Б не увеличивает счётчик. Предложение
совпадения необязательно; решение принимает сам жилец.

### 6. Ответ УК, статусы и повторное открытие

1. Представитель УК открывает «Проблемы» и **первую подъездную карточку о
   лифте из сценария 3**, которую поддержал Б. На широком экране карточка
   может быть строкой списка. Нажимает «Ответить жильцам»: экран прокрутится
   к полю «Официальный ответ». Пишет, например, «Заявку увидели, проверяем
   лифт» и нажимает «Отправить ответ». Последний ответ показан отдельным
   блоком «Официальный ответ» над блоком «Обсуждение».
2. В той же карточке нажимает «Изменить статус». В блоке «Обновить карточку»
   выбирает в поле «Статус» значение «В работе», в «Пояснение» пишет, например,
   «Мастер вызван», затем нажимает «Сохранить обновление».
3. В той же карточке нажимает «Закрыть проблему»; в «Обновить карточку»
   выставляет «Статус» = «Закрыта», «Результат закрытия» = «Решена» и
   обязательное «Пояснение» = «Лифт проверен и снова работает». Нажимает
   «Сохранить обновление».
4. Жилец А открывает «Проблемы» → вкладку «Закрытые» → **эту же карточку о
   лифте**. Внизу находит «Проблема осталась?», пишет в поле «Что не решено»
   «Лифт снова остановился» и нажимает «Переоткрыть».

**Ожидается:** ответ, статусы и пояснения видны обоим жильцам. После шага 4
статус вновь «Открыта» и история изменений сохранена. Переоткрыть может
автор А, но не Б, который лишь поддержал карточку.

### 7. Объединение карточек сотрудником УК

1. Проверьте, что первая карточка А о лифте из сценария 3 **открыта** после
   сценария 6. Жилец Б нажимает «Создать», заполняет категорию «Лифт»,
   описание «Лифт в нашем подъезде не приезжает после нажатия кнопки. Кабина
   остается внизу.», область «Подъезд», подъезд `1` → «Продолжить».
2. На экране проверки Б намеренно нажимает «Создать заявку», **даже если**
   интерфейс предлагает первую карточку. Так появляется **вторая открытая
   подъездная карточка Б** для ручной проверки объединения УК.
3. Представитель УК открывает «Проблемы» → **первую, более раннюю карточку А**
   о лифте. Внизу разворачивает «Объединить с другой проблемой». При наличии
   доступа к GigaChat может нажать «Найти похожие проблемы»: ИИ попробует
   предложить вариант. При недоступности GigaChat используется локальный
   поиск; ни одна подсказка не объединяет карточки автоматически.
4. В поле «Вторая открытая карточка этого дома» выбирает **новую карточку Б
   из шага 2**. Проверяет обе карточки в предварительном просмотре, поля
   «Итоговое название» и «Итоговый статус», при желании заполняет «Пояснение».
   Ставит флажок «Я проверил обе карточки и хочу объединить их» и нажимает
   «Объединить карточки».
5. Открывает итоговую карточку и проверяет сообщения, исходные обращения,
   вложения и список поддержавших. Ссылка на присоединённую карточку Б должна
   вести к итоговой.

**Ожидается:** основной остаётся более ранняя карточка А. Поддержка одного
человека не удваивается при объединении. Закрытые карточки нельзя выбрать
как вторую открытую проблему.

### 8. Уведомления и текстовый бот

1. После ответа или изменения статуса из сценария 6 жилец А открывает
   мини-приложение, нажимает значок «Уведомления» на главной странице и в
   списке выбирает соответствующее событие. Кнопка «Открыть проблему» ведёт
   в карточку о лифте; аналогичные события по доступу ведут в заявку через
   «Открыть заявку». «Прочитать все» снимает отметки непрочитанного.
2. В карточке о лифте жилец А находит блок «Сообщения бота» и выключает
   сообщения **только по этой карточке**. Возвращается в «Уведомления»:
   запись в мини-приложении остаётся доступной.
3. В чате бота MAX жилец А отправляет `/start`: бот показывает меню с
   кнопками. Для текстового пути к тем же данным использует `/issuehelp`
   (проблемы), `/access help` (доступы) и `/notificationhelp` (уведомления).
   Например, открывает список проблем через меню бота и сверяет статус
   карточки о лифте с мини-приложением.
4. Представитель УК также получает сообщение бота о новой заявке либо
   открывает её из меню бота. Проверяет, что изменение одной и той же
   карточки видно в обоих интерфейсах.

**Ожидается:** бот и мини-приложение работают с одной БД. Отключение сообщений
бота по карточке не удаляет уведомления из мини-приложения.

### 9. Права сотрудников УК

1. Подготовьте четвёртый, ещё не назначенный аккаунт MAX с отдельным номером.
   Представитель УК открывает «Доступы» → вкладку «Сотрудники» → блок
   «Добавить или изменить сотрудника».
2. В «Номер телефона» вводит номер четвёртого аккаунта. Для наглядной
   проверки отмечает только «Вести проблемы и отвечать официально» и
   нажимает «Сохранить назначение». Два других права — «Управлять
   сотрудниками и правами» и «Рассматривать заявки жильцов и выдавать
   доступ» — оставляет выключенными.
3. В списке сотрудников проверяет новое назначение: до входа человека может
   стоять пометка «ожидает входа». Новый сотрудник открывает мини-приложение
   **со своего аккаунта MAX** и подтверждает именно назначенный номер.
4. Новый сотрудник открывает «Проблемы», вносит ответ в карточку и проверяет,
   что действия по выдаче доступа жильцам и управлению сотрудниками ему
   недоступны. Представитель УК в «Сотрудники» проверяет, что не может
   изменить или отозвать **собственное** назначение.

**Ожидается:** права назначаются по номеру и связываются с аккаунтом после
подтверждения. Для приглашённого не создаётся общий пароль и не требуется
отдельное принятие назначения.

### 10. Предложение доступа и отмена заявки

1. Представитель УК открывает «Доступы» → «Жильцы» → блок «Предложить доступ
   по номеру». Выбирает тестовый дом, вводит подтверждённый номер жильца Б,
   подъезд `1`, квартиру `14`, срок «Постоянный» и нажимает «Отправить
   предложение».
2. Жилец Б открывает нижнюю вкладку «Доступ», прокручивает страницу «Доступ
   к дому» до блока «Предложения от УК» и находит предложение для квартиры
   14. Нажимает «Принять» и проверяет квартиру в
   своих доступах. Для проверки альтернативы можно создать отдельное
   предложение и нажать «Отклонить»: отклонённое не выдаёт доступ.
3. Для проверки самостоятельной отмены Б открывает нижнюю вкладку «Доступ».
   В форме вверху экрана «Доступ к дому» выбирает тот же дом и подтверждает
   адрес, вводит подъезд `1` и **квартиру 15**, нажимает «Отправить заявку в
   УК». Затем в нижней вкладке «Доступ» прокручивает до блока «Мои заявки»,
   находит заявку квартиры 15 и нажимает «Отменить заявку» → флажок
   «Подтверждаю отмену заявки на доступ к дому» → «Подтвердить отмену».
4. Для согласованной отмены Б тем же способом подаёт **новую заявку на
   квартиру 16**. Представитель УК: «Доступы» → «Жильцы» → «Заявки на
   доступ» → заявка квартиры 16 → «Обсуждение» → «Рабочий статус» =
   «На рассмотрении» → «Сохранить статус».
5. Б: нижняя вкладка «Доступ» → прокрутить до «Мои заявки» → заявка
   квартиры 16 → «Открыть заявку» → «Запросить отмену». Представитель УК
   снова открывает обсуждение **той же
   заявки квартиры 16** и нажимает «Подтвердить отмену».

**Ожидается:** предложение само по себе не выдаёт доступ; он появляется
после принятия. Открытую заявку автор отменяет сам. После начала рассмотрения
отмена требует подтверждения другой стороны, а обсуждение сохраняется.

## Собственный API

- Базовый HTTPS-адрес: <https://168.113.209.86>.
- Интерактивная документация Swagger UI: <https://168.113.209.86/docs>.
- Машиночитаемое описание методов и форматов OpenAPI 3.1:
  <https://168.113.209.86/openapi.json> и [файл в репозитории](openapi.json).
- Последовательность девяти проверок с ролями, параметрами и ожидаемыми
  ответами: [DATA-API.yaml](DATA-API.yaml).

OpenAPI описывает доступные методы, тела запросов и ответы. DATA-API.yaml
задаёт конкретные контрольные запросы для сценария выше; файлы выполняют
разные задачи. Для проверки полного API используется корневой `openapi.json`,
включая маршруты файлов, администрирования и служебных проверок.
Проверки DATA-API воспроизводят действия сценариев 2–6 на **свежих данных**,
а не повторяются после них на той же квартире: повторная выдача уже
существующего доступа возвращает `409`.

Закрытые маршруты требуют заголовок `X-Max-Init-Data` со свежими подписанными
данными запуска **соответствующего** аккаунта MAX. Он не является постоянным
API-ключом; срок действия — один час. Для прямой проверки API данные можно
взять из `window.WebApp.initData` в открытом через MAX мини-приложении, не
публикуя их. `DATA-API.yaml` использует переменные вместо реальных значений.
`HOUSE_ID` берётся из поиска дома, `CATEGORY_ID` — из списка категорий,
`REQUEST_ID` и `CARD_ID` — из предыдущих ответов. Для POST-запросов нужны
разные `Idempotency-Key`: повтор с тем же ключом может вернуть `409`.
