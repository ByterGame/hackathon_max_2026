# СвойДом

## Сервис обращений жителей и УК в MAX

Житель подаёт заявку на доступ к дому, сообщает о проблеме, поддерживает
похожую карточку и следит за ответами. Сотрудник УК выдаёт доступ, ведёт
карточки и назначает права сотрудникам. Наша поддержка через бота подключает
УК и её дома. Мини-приложение и текстовые команды бота работают с одной
PostgreSQL.

Состав решения: React/Vite собирает интерфейс мини-приложения; FastAPI отдаёт
интерфейс, HTTP API и приватные вложения; отдельный процесс бота принимает
сообщения MAX; PostgreSQL хранит аккаунты, дома, заявки и обсуждения. Перед
стартом веб-сервиса Compose применяет миграции Alembic. На сервере Nginx
принимает HTTPS-запросы и передаёт их FastAPI; сам Nginx в Compose не входит.
Для сдачи проекта см. [инструкцию и контрольный список](SUBMISSION.md).
Публичный HTTPS-адрес мини-приложения и API на текущем VPS:
<https://168.113.209.86/>. Для входа открывайте мини-приложение из бота MAX:
обычный переход по адресу в браузере не создаёт подписанные данные запуска.

Для запуска нужен файл `.env` в корне репозитория. Для нового файла используйте
`.env.example` как образец; существующий `.env` не перезаписывайте. Обязательны
`BOT_TOKEN`, `PORT`, все `DB_*`, `FILE_STORAGE_ROOT`, `ISSUE_AI_PROVIDER`,
`GIGACHAT_SEND_REAL_DATA`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`,
`GIGACHAT_AUTH_URL` и `GIGACHAT_VERIFY_SSL`. Для обязательных параметров
Compose не подставляет значения по умолчанию. В образце `BOT_TOKEN`, `PORT`, `DB_*` и
`FILE_STORAGE_ROOT` оставлены пустыми: заполните их явно. Для запуска в
Compose можно выбрать `PORT=8000`, `DB_HOST=db`, `DB_PORT=5432`,
`DB_NAME=hackathon`, `DB_USER=hackathon`,
`FILE_STORAGE_ROOT=/data/private_files` и свой пароль БД. Случайный пароль
можно получить командой `openssl rand -hex 24`. Файл `.env` не должен попадать
в Git. Если `.env` уже существует на VPS, дополните его новыми переменными до
следующего `docker compose up`, не заменяя образцом.
`GIGACHAT_AUTH_KEY` и `GIGACHAT_CA_BUNDLE` тоже должны присутствовать в файле,
но до настройки внешнего сервиса их значения можно оставить пустыми.

Сборка и запуск PostgreSQL, миграций, HTTP-сервиса и бота:

```sh
docker compose up --build
```

Сервис `migrate` завершается перед стартом приложения и бота. Бот запускается
отдельным контейнером из того же образа и получает сообщения через опрос MAX;
ему не нужен открытый порт.
Состояние контейнеров и сообщения бота можно посмотреть командами
`docker compose ps` и `docker compose logs -f bot`. Не запускайте второго
бота с тем же токеном одновременно.

### Подсказки GigaChat

В образце выбран `ISSUE_AI_PROVIDER=gigachat`, а
`GIGACHAT_SEND_REAL_DATA=0` и `GIGACHAT_AUTH_KEY` пустой. В таком состоянии
заявки продолжают создаваться с локальной подсказкой: описание жителя наружу
не отправляется. Когда получите ключ авторизации GigaChat API и примете
решение об отправке описаний, укажите в `.env` ключ и явно установите
`GIGACHAT_SEND_REAL_DATA=1`. До этого момента ключ для запуска не нужен.

`GIGACHAT_SCOPE` должен соответствовать ключу: `GIGACHAT_API_PERS` для
физического лица, `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP` для организации.
`GIGACHAT_MODEL` задаёт доступную аккаунту модель; пример использует
`GigaChat-2-Pro`. `GIGACHAT_AUTH_URL` в образце указывает на актуальный
`https://api.giga.chat/api/v2/oauth`. Значения сверьте с
[документацией авторизации GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api)
и [списком моделей](https://developers.sber.ru/docs/ru/gigachat/guides/selecting-a-model).
`ISSUE_AI_PROVIDER=local` отключает внешний вызов независимо от наличия ключа.
Токен доступа GigaChat действует 30 минут по документации провайдера; сервис
кэширует его в памяти процесса и обновляет незадолго до истечения срока.
Перед включением передачи реальных обращений проверьте условия использования
и правила обработки данных. При недоступности GigaChat сервис использует
локальную подсказку и записывает причину переключения в журнал.

При `GIGACHAT_VERIFY_SSL=1` проверка TLS для GigaChat включена: необходим
доверенный корневой сертификат Минцифры по
[инструкции GigaChat](https://developers.sber.ru/docs/ru/gigachat/certificates).
Если его нет в стандартном хранилище контейнера, получите официальный PEM
по этой инструкции и разместите файл на VPS вне репозитория, например
`/opt/hackathon/certs/gigachat-ca.pem`. Проверьте файл и соединение на VPS:

```sh
openssl x509 -in /opt/hackathon/certs/gigachat-ca.pem -noout -subject -issuer -dates
openssl s_client -connect api.giga.chat:443 -servername api.giga.chat -verify_hostname api.giga.chat -verify_return_error -CAfile /opt/hackathon/certs/gigachat-ca.pem </dev/null
```

Во второй проверке ожидается `Verify return code: 0 (ok)`. Если для цепочки
нужен также выпускающий сертификат, используйте PEM-набор с необходимыми
доверенными сертификатами. Для временной диагностики можно установить
`GIGACHAT_VERIFY_SSL=0`: проверка сертификата отключится только для запросов
к GigaChat (получения токена и вызова модели). В таком режиме сервер нельзя
удостоверить, поэтому ключ и тексты обращений могут быть перехвачены;
верните `1` после диагностики. Ошибку HTTP 403 отключение TLS не исправляет.
Чтобы передать PEM в `app` и `bot` только для чтения, скопируйте на VPS
`compose.gigachat-ca.example.yaml` в `compose.gigachat-ca.yaml`, затем задайте
в `.env`:

```dotenv
GIGACHAT_CA_HOST_PATH=/opt/hackathon/certs/gigachat-ca.pem
GIGACHAT_CA_BUNDLE=/run/gigachat/ca-bundle.pem
```

Запускайте оба Compose-файла вместе:

```sh
docker compose -f compose.yaml -f compose.gigachat-ca.yaml up --build
```

Без дополнительного сертификата оставьте `GIGACHAT_CA_BUNDLE` и
`GIGACHAT_CA_HOST_PATH` пустыми и используйте обычный `docker compose up --build`.
При `GIGACHAT_VERIFY_SSL=0` дополнительный сертификат также не требуется.

При `PORT=8000` интерфейс и проверки доступны по адресам `http://localhost:8000/`,
`http://localhost:8000/service/health` (работает веб-сервис) и
`http://localhost:8000/service/ready` (есть соединение с БД).
Живой контракт доступен по `http://localhost:8000/openapi.json` и включает
потоковые маршруты файлов. Полный снимок этого контракта для сдачи хранится в
[openapi.json](openapi.json); после изменения API обновите его командой
`cd backend && python -m tools.export_runtime_openapi`. Внутренний
`backend/openapi.yaml` описывает только маршруты, проходящие через
кодогенератор, поэтому для внешней проверки используйте полный снимок или
живой `/openapi.json`. Для запросов от имени пользователя нужны свежие
подписанные данные запуска MAX в заголовке `X-Max-Init-Data`.
Порт приложения задаётся переменной `PORT` в `.env` и в Compose привязан к
`127.0.0.1` хоста: для доступа извне нужен настроенный обратный прокси (на
текущем VPS это Nginx с HTTPS).
PostgreSQL хранит данные в томе `postgres_data`, приватные вложения — в томе
`private_files`; Nginx к нему напрямую не обращается. Порт БД не опубликован на
хосте: приложение подключается к `db` на порту `DB_PORT` во внутренней сети
Compose. `docker compose down` сохраняет том; вариант с `-v` удалит том
вместе со всеми данными.
В БД сохраняются внутренние идентификаторы и подтверждённые через MAX номера
пользователей, привязки к домам, заявки, статусы и обсуждения. Вложения лежат
отдельно от БД и выдаются через API после проверки доступа к карточке или
заявке. Исходные тексты обращений по умолчанию не передаются GigaChat:
передача включается только явным `GIGACHAT_SEND_REAL_DATA=1`.

После первого запуска будущий главный администратор узнаёт свой MAX ID командой
`/whoami` у бота. После применения миграций администратор сервера назначает
этот аккаунт из контейнера приложения:

```sh
docker compose exec app python -m src.cli.bootstrap_admin <MAX_USER_ID>
```

Это доверенная команда: сверяйте MAX ID и не запускайте её с чужим ID. Она может
повысить нейтральный аккаунт или существующего оператора поддержки, но не жителя
и не сотрудника УК. Роли администратора и поддержки различны. Администратор
видит данные сервиса и управляет ими через мини-приложение или `/admin` в боте;
оператор поддержки только разбирает обращения УК и домов. Оператора добавляют
из админки по номеру: он подтверждает этот номер через MAX и сам принимает
приглашение. Права не выдаются только по введённому номеру. Пользователи
подтверждают свой номер контактом MAX; один аккаунт не может одновременно быть
жителем и сотрудником УК.

Для проверки основного сценария нужны три отдельных тестовых аккаунта MAX:
представитель УК и два жителя с подтверждёнными номерами. Аккаунты и номера
принадлежат проверяющим; заранее создать работающие логины и пароли нельзя,
поскольку вход привязан к MAX. Поддержка нужна отдельно, если проверяется
штатная регистрация УК без тестового режима. Вымышленные сведения для ручного
ввода находятся в [submission/test-data.json](submission/test-data.json);
реальных телефонов и токенов в файле нет.

Пошаговая проверка на пустой тестовой базе:

1. Представитель УК открывает мини-приложение из MAX, подтверждает свой номер,
   подаёт заявку на УК и подключение дома из тестовых данных. Поддержка
   одобряет обе заявки; либо временный тестовый режим позволяет представителю
   подтвердить собственную регистрацию. Ожидаемый результат — дом появляется
   в поиске и кабинете УК.
2. Оба жителя открывают приложение из своих аккаунтов MAX, подтверждают номера
   и подают отдельные заявки на этот дом, указывая ФИО, подъезд и квартиру.
   Ожидаемый результат — заявки видны сотруднику УК, но проблемы жителям ещё
   недоступны.
3. Сотрудник УК одобряет оба доступа. Ожидаемый результат — дом появляется у
   жителей в «Моих домах», им доступно создание проблем.
4. Первый житель сообщает о проблеме лифта в своём подъезде. Второй житель
   видит карточку и поддерживает её. Ожидаемый результат — одна общая карточка
   с двумя участниками, а не две одинаковые.
5. Сотрудник УК отвечает в обсуждении и переводит карточку «В работе» с
   пояснением. Ожидаемый результат — новый статус и ответ видны обоим жителям.
   Проверьте карточку и уведомления в мини-приложении и в боте через
   `/access help`, `/issuehelp`, `/notificationhelp`.

Это сценарий проверки, а не утверждение, что он уже пройден на текущем VPS.
При повторном прогоне используйте другой вымышленный номер дома: уже
подключённый адрес нельзя зарегистрировать второй раз. При тестировании
вложений доступны команды `/filehelp`, `/files UUID_карточки` и
`/files access UUID_заявки`; бот повторно проверяет права перед отправкой.

Для проверки без участия поддержки можно временно указать `TEST_MODE=1` в
серверном `.env` и пересоздать контейнер `app`. Тогда после подачи заявки УК
появится выделенная кнопка тестового подтверждения: она создаст УК, назначит
заявителя первым сотрудником и подключит все указанные в этой заявке дома.
Номер первого сотрудника при этом должен совпадать с подтверждённым через MAX
номером заявителя. В обычном режиме (`TEST_MODE=0`, значение по умолчанию)
маршрут возвращает `404`, а УК и дома по-прежнему подтверждает поддержка.
Отключите тестовый режим после проверки; для работающего сервиса без проверки
документов этот обход использовать нельзя.

Внешние условия и известные ограничения: нужен доступ проверяющих к MAX и
действующий токен бота; серверу нужен HTTPS для мини-приложения. GigaChat
необязателен для создания заявки: без ключа или при ошибке API используется
локальная подсказка, которая может быть менее точной. Проверка документов и
«Госуслуг» не реализована, срочность проблем не рассчитывается. Тестовый
режим не заменяет подтверждение номера через MAX. Холодную сборку Docker за
5 минут необходимо отдельно измерить на машине сдачи; локально она пока не
проверена.

Остановить сервис без удаления данных можно командой `docker compose down`.
Повторный запуск после изменения кода — `docker compose up -d --build`; если
код и образы не менялись, достаточно `docker compose up -d`. Проверьте
`docker compose ps` и `/service/ready` после запуска. Не используйте
`docker compose down -v` для обычной остановки: это удалит БД и вложения.

Для диагностики используйте `docker compose logs --tail=200 app bot`.
Новые записи имеют формат JSON: `event` указывает этап, `error_code` — вид
сбоя, `exception_message` — очищенный текст ошибки, `stack` — место её
возникновения. `request_id` связывает HTTP-запрос или событие бота с вложенными
записями, например обращением к GigaChat. У HTTP-запроса этот ID также возвращается
в заголовке `X-Request-ID`. Тексты заявок, номера и ключи намеренно не пишутся
в логи; при передаче журнала другим людям всё равно проверяйте его содержимое.

Для изменяющих HTTP-запросов можно передавать `Idempotency-Key` — ключ одного
логического действия длиной 16–128 символов. При сетевом повторе используйте
тот же ключ и тело запроса. Первый успешный запрос сохраняет ключ и изменение
вместе; повтор вернёт `409`, после чего нужно перечитать состояние. Сервер не
возвращает прежний ответ повторно, а запросы без ключа от повторов не защищены.
Загрузка файлов использует отдельный потоковый маршрут; её повторная отправка
может сохранить второй файл. Допустимые форматы, предел 8 МиБ и проверка прав
описаны в [контракте вложений](backend/docs/files/README.md). При настройке
Nginx на VPS задайте `client_max_body_size 10m;` в блоке `server`, который
проксирует приложение, и проверьте конфигурацию командой `sudo nginx -t` перед
`sudo systemctl reload nginx`. Иначе файл допустимого размера может получить
ответ `413 Request Entity Too Large` до попадания в приложение. Конфигурация
Nginx хранится на VPS, в этом репозитории её нет.

Для разработки бэкенда вне Docker потребуется отдельный локальный PostgreSQL.
Значение `DB_HOST=db` работает только внутри Compose: при локальном
запуске задайте адрес этого PostgreSQL в `DB_HOST` и его порт в `DB_PORT`.
Затем примените миграции и запустите процессы в отдельных терминалах:

```sh
cd backend && alembic -c alembic.ini upgrade head
cd backend && python -m src
cd backend && python -m src.bot.main
cd miniapp && npm install && npm run dev
```

Не запускайте локального бота одновременно с контейнерным при одном токене.
В браузере вне MAX серверный вход не сработает; для проверки вёрстки можно
собрать мини-приложение с `VITE_DEMO_MODE=true`, но это отдельный локальный
режим с данными браузера, не проверка API.

## Установка зависимостей

Python 3.12, активированное виртуальное окружение. Команды из корня репозитория.

Бэкенд:

```sh
python -m pip install -r backend/requirements.txt
```

Инструменты кодогенерации:

```sh
python -m pip install -r backend/tools/codegen/requirements.txt
```

[Структура и запуск](backend/docs/README.md) · [Кодогенерация](backend/docs/codegen.md)

## Git-хуки

Один раз для локального клона подключите общие хуки репозитория:

```sh
git config core.hooksPath .githooks
```

Перед коммитом выполняется `python -m tools.codegen --check`: проверяются
контракты и актуальность сгенерированных файлов. Перед отправкой изменений
в удалённый репозиторий запускается полный набор тестов бэкенда.
Хуки используют активированное виртуальное окружение или `.venv` в корне
репозитория.
