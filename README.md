# hackathon_max_2026

## Сервис обращений жителей и УК в MAX

Житель подаёт заявку на доступ к дому, сообщает о проблеме, поддерживает
похожую карточку и следит за ответами. Сотрудник УК выдаёт доступ, ведёт
карточки и назначает права сотрудникам. Наша поддержка через бота подключает
УК и её дома. Мини-приложение и текстовые команды бота работают с одной
PostgreSQL.

Для запуска нужен файл `.env` в корне репозитория. Для нового файла используйте
`.env.example` как образец; существующий `.env` не перезаписывайте. Обязательны
`BOT_TOKEN`, `PORT`, все `DB_*` и `FILE_STORAGE_ROOT`. Случайный пароль БД можно получить командой
`openssl rand -hex 24`. Файл `.env` не должен попадать в Git. `GROQ_API_KEY`
необязателен; пока `GROQ_SEND_REAL_DATA=0`, тексты жителей во внешний ИИ не
отправляются, а подсказка формируется локально.
Если `.env` уже существует на VPS, добавьте в него
`FILE_STORAGE_ROOT=/data/private_files` перед следующим запуском Compose.

Сборка и запуск PostgreSQL, миграций, HTTP-сервиса и бота:

```sh
docker compose up --build
```

Сервис `migrate` завершается перед стартом приложения и бота. Бот запускается
отдельным контейнером из того же образа и получает сообщения через опрос MAX;
ему не нужен открытый порт.
Состояние контейнеров и сообщения бота можно посмотреть командами
`docker compose ps` и `docker compose logs -f bot`. Не запускайте второго
бота с тем же токеном одновременно.

При `PORT=8000` интерфейс и проверки доступны по адресам `http://localhost:8000/`,
`http://localhost:8000/service/health` (работает веб-сервис) и
`http://localhost:8000/service/ready` (есть соединение с БД).
Живой контракт доступен по `http://localhost:8000/openapi.json` и включает
потоковые маршруты файлов. Сгенерированный `backend/openapi.yaml` пока содержит
старые демонстрационные пути, отключённые в работающем приложении; для проверки
нового API используйте живой контракт.
Порт приложения задаётся переменной `PORT` в `.env` и в Compose привязан к
`127.0.0.1` хоста: для доступа извне нужен настроенный обратный прокси (на
текущем VPS это Nginx с HTTPS).
PostgreSQL хранит данные в томе `postgres_data`, приватные вложения — в томе
`private_files`; Nginx к нему напрямую не обращается. Порт БД не опубликован на
хосте: приложение подключается к `db` на порту `DB_PORT` во внутренней сети
Compose. `docker compose down` сохраняет том; вариант с `-v` удалит том
вместе со всеми данными.

После первого запуска будущий главный администратор узнаёт свой MAX ID командой
`/whoami` у бота. После применения миграций администратор сервера назначает
этот аккаунт из контейнера приложения:

```sh
docker compose exec app python -m src.cli.bootstrap_admin <MAX_USER_ID>
```

Это доверенная команда: сверяйте MAX ID и не запускайте её с чужим ID. Она может
повысить нейтральный аккаунт или существующего оператора поддержки, но не жителя
и не сотрудника УК. Роли администратора и поддержки различны. Администратор
видит данные сервиса и управляет ими через мини-приложение или `/admin` в боте;
оператор поддержки только разбирает обращения УК и домов. Оператора добавляют
из админки по номеру: он подтверждает этот номер через MAX и сам принимает
приглашение. Права не выдаются только по введённому номеру. Пользователи
подтверждают свой номер контактом MAX; один аккаунт не может одновременно быть
жителем и сотрудником УК.

Для ручной сквозной проверки после запуска нужны отдельные тестовые аккаунты
MAX администратора, поддержки, представителя УК и жителя. Поддержка сначала одобряет обращение
УК и её заявку на дом; сотрудник с подтверждённым номером рассматривает заявку
жителя на доступ. После выдачи доступа житель создаёт проблему, второй житель
поддерживает её, а сотрудник отвечает и переводит статус. Проверяйте результат
в обоих каналах — в мини-приложении и командами `/access help`, `/issuehelp`,
`/drafthelp`, `/notificationhelp`, `/filehelp`, `/files UUID_карточки` у бота.
Вложения бот отправляет только после повторной проверки доступа. Это инструкция
для проверки, а не утверждение, что сценарий уже пройден на текущем VPS.

Для диагностики используйте `docker compose logs --tail=200 app bot`.
Новые записи имеют формат JSON: `event` указывает этап, `error_code` — вид
сбоя, `exception_message` — очищенный текст ошибки, `stack` — место её
возникновения. `request_id` связывает HTTP-запрос или событие бота с вложенными
записями, например обращением к Groq. У HTTP-запроса этот ID также возвращается
в заголовке `X-Request-ID`. Тексты заявок, номера и ключи намеренно не пишутся
в логи; при передаче журнала другим людям всё равно проверяйте его содержимое.

Для изменяющих HTTP-запросов можно передавать `Idempotency-Key` — ключ одного
логического действия длиной 16–128 символов. При сетевом повторе используйте
тот же ключ и тело запроса. Первый успешный запрос сохраняет ключ и изменение
вместе; повтор вернёт `409`, после чего нужно перечитать состояние. Сервер не
возвращает прежний ответ повторно, а запросы без ключа от повторов не защищены.
Загрузка файлов использует отдельный потоковый маршрут; её повторная отправка
может сохранить второй файл. Допустимые форматы, предел 8 МиБ и проверка прав
описаны в [контракте вложений](backend/docs/files/README.md). При настройке
Nginx для этого маршрута нужно разрешить тело запроса не меньше 8 МиБ.

Для разработки бэкенда вне Docker потребуется отдельный локальный PostgreSQL.
Значение `DB_HOST=db` из образца работает только внутри Compose: при локальном
запуске задайте адрес этого PostgreSQL в `DB_HOST` и его порт в `DB_PORT`.
Затем примените миграции и запустите процессы в отдельных терминалах:

```sh
cd backend && alembic -c alembic.ini upgrade head
cd backend && python -m src
cd backend && python -m src.bot.main
cd miniapp && npm install && npm run dev
```

Не запускайте локального бота одновременно с контейнерным при одном токене.
В браузере вне MAX серверный вход не сработает; для проверки вёрстки можно
собрать мини-приложение с `VITE_DEMO_MODE=true`, но это отдельный локальный
режим с данными браузера, не проверка API.

## Установка зависимостей

Python 3.12, активированное виртуальное окружение. Команды из корня репозитория.

Бэкенд:

```sh
python -m pip install -r backend/requirements.txt
```

Инструменты кодогенерации:

```sh
python -m pip install -r backend/tools/codegen/requirements.txt
```

[Структура и запуск](backend/docs/README.md) · [Кодогенерация](backend/docs/codegen.md)

## Git-хуки

Один раз для локального клона подключите общие хуки репозитория:

```sh
git config core.hooksPath .githooks
```

Перед коммитом выполняется `python -m tools.codegen --check`: проверяются
контракты и актуальность сгенерированных файлов. Перед отправкой изменений
в удалённый репозиторий запускается полный набор тестов бэкенда.
Хуки используют активированное виртуальное окружение или `.venv` в корне
репозитория.
